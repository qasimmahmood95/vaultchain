----- knee-point analysis (approval contention) -----
The table above is a textbook single-server queue saturating:

  * Throughput climbs steeply while concurrency is below the service ceiling
    (75 -> 128 -> 210 -> 341 rps between levels 2 and 32), then flattens:
    513 rps at 128, 596 at 256, 598 at 512 — the last doubling of offered
    concurrency bought +0.4% throughput.
  * Latency tells the same story from the other side: p95 roughly doubles per
    level once saturated (242ms @128 -> 409ms @256 -> 852ms @512), i.e. each
    request's latency is its QUEUE POSITION times a ~1.7-2ms service time,
    exactly what one pooled SQLite connection (D35) predicts.
  * This evidence run puts the knee (first level at >=90% of max throughput)
    at concurrency 256; across the runs captured this session it landed at
    128, 256, and 512 with max throughput in the 500-630 rps band. The knee
    is therefore recorded as a BAND (~128-512 on this 12-core machine), not a
    constant — perf/baselines.json stores kneeConcurrency as informational,
    deliberately not a threshold (PERFORMANCE.md).
  * The envelope stops at 512 on purpose: p95 there (~0.85-1.6s across runs)
    approaches Prisma's default 2s transaction-acquisition timeout, past
    which the failure mode changes from "slow" to "timeout" — a different,
    documented cliff.
  * The correctness bar never moved while all of that happened: at every
    level including 512 simultaneous attempts, exactly two approvals won
    (dual-approval policy), every loser got its designed 409, the DB sweep
    found zero duplicate (transactionId, approver) rows, and there was not
    one 5xx in this run's 3,066 contended requests (sum of levels x 3 reps)
    — nor in any other perf run captured this session.
